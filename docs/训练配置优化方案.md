# 训练配置优化方案

## 结论

当前不再推荐 `micro_batch_size`，也不再把 `batch_size=32` 作为默认提速方案。

当前目标服务器配置：

| 资源 | 配置 |
|---|---|
| GPU | NVIDIA RTX5880, 48 GiB 显存 |
| CPU | AMD vCPU, 32 核 |
| 内存 | 64 GB |

GPU 架构事实（影响后续加速选项的可用性）：

- RTX 5880 属于 **Ada Lovelace 架构（AD102 核心，Compute Capability 8.9）**，不是 Blackwell。
- 第四代 Tensor Core，原生支持 TF32 / FP16 / **BF16** / FP8。BF16 可用是后续候选 G 的前提。
- "32 核 vCPU" 通常是**逻辑核（含超线程）**，DataLoader worker 的有效上限受**物理核数**约束，而非逻辑核数；worker sweep 前应先确认物理核数（下文 B 方案）。

PhaseWindowTCN 的显存高主要来自三窗口输入：`full`、`exposure`、`recovery` 都会重采样到完整时间长度并堆叠，随后分别进入波形编码器。batch 变大时激活显存近似线性上升；旧 24 GiB 环境下 `batch_size=32` 已出现 OOM。新服务器有 48 GiB 显存，`batch_size=24/32` 可以重新进入候选实测，但仍不能跳过基线对照直接写入正式配置。

当前正式诊断批的默认训练口径是：

| 参数 | 当前值 | 说明 |
|---|---:|---|
| `batch_size` | 16 | 当前可运行基线；48 GiB 环境可候选测试 24/32 |
| `num_workers` | 2 | 保守基线；有效上限受物理核数约束，候选测试 4/8（见 B 方案） |
| `pin_memory` | true | CUDA 训练保留 |
| `persistent_workers` | false | 避免常驻 worker 带来额外内存压力 |
| `prefetch_factor` | 2 | 仅在 `num_workers > 0` 时生效 |
| `epochs` | 80 | 保留诊断批上限 |
| `early_stopping.patience` | 10 | 减少无效训练 |
| `amp` | `enabled=true`, `dtype=float16` | 已启用 |
| `performance.tf32` | true | 已启用，并在代码中同步设置 matmul precision |
| `performance.cudnn_benchmark` | true | 固定输入尺寸下启用 cuDNN autotuner |
| `performance.compile` | false | 仅作为候选实验开启 |

适用配置：

- `configs/experiment/phase_window_tcn_ablation/phase_window_tcn_ablation.json`
- `configs/experiment/phase_window_tcn_ablation/phase_window_tcn_ablation_structure.json`
- `configs/experiment/phase_window_tcn_ablation/phase_window_tcn_ablation_followup.json`
- `configs/experiment/phase_window_tcn_improvement/phase_window_tcn_improvement.json`

## 已完成的代码级加速

### TF32 配置补全

`performance.tf32=true` 时，代码现在同时设置：

- `torch.backends.cuda.matmul.allow_tf32 = true`
- `torch.backends.cudnn.allow_tf32 = true`
- `torch.set_float32_matmul_precision("high")`

目的：让当前配置真正覆盖 FP32 matmul 路径，减少只开 backend flag 但 matmul precision 仍保守的情况。

### 验证阶段使用 inference mode

`Trainer.evaluate()` 和 `Trainer.predict()` 已从 `torch.no_grad()` 改为 `torch.inference_mode()`。

目的：降低 validation 和最终评估的 autograd 元数据开销；不改变训练反传路径。

### 训练循环已消除 per-batch CPU 同步点

`Trainer.fit()` 在设备上用 `loss_accum` 累积 loss，epoch 末才取标量，避免 per-batch `.item()` 强制 CUDA 同步（见 `src/dl/training/trainer.py` 训练循环注释）。这是零成本加速，已在基线中生效。

注意：`evaluate()` 仍保留 per-batch `loss.item()`（验证阶段，每 epoch 仅一次），属于可接受开销，不在本轮加速范围。

### AMP dtype 已支持 BF16

`AmpConfig.dtype` 支持 `float16` 和 `bfloat16`（见 `src/dl/training/trainer.py` 的 `_validate_amp`）。当前正式配置用 FP16 + GradScaler；若切换 BF16，理论上不需要 GradScaler（BF16 与 FP32 同指数位，无下溢风险），但当前代码在 `amp.enabled=true` 时仍会初始化 `GradScaler(enabled=True)`——BF16 下 GradScaler 退化为 no-op 不影响正确性，但候选 G 落地前需复核一次（见候选 G）。

## 候选加速方案

## 省时执行策略（按时计费服务器）

当前服务器按时收费时，优化实验采用“两层验收”：

1. **正式基线层**：已经启动的 Phase 1 `phase_window_tcn_ablation` 批次继续跑完，作为唯一正式 A/B1 基线；不要为了后续候选重复运行相同的 `float16 + batch16 + workers2 + compile=false` 配置。
2. **候选筛选层**：G/B/D/C 候选先只跑一个代表性 run，用于判断速度、显存和明显收敛风险；筛选失败即停止，不扩展到 4 个 Phase 1 run。
3. **转正复验层**：只有候选筛选通过，才对关键 run 做最小复验；只有准备写入正式配置时，才需要做完整 Phase 1 回归或联合回归。

代表性 run 默认选 `phase_window_tcn_gas_varweight`，理由是它仍使用 PhaseWindowTCN 三窗口主模型，同时比 `free_component_mse` 更能代表后续 N2 诊断方向。若当前已经跑完或正在跑的是另一个 PhaseWindowTCN run，也可以直接把该 run 作为筛选基线，避免重跑。

本项目当前 `pipeline.run_experiment` 不提供 `--only-run` 或自动跳过已完成 run。需要单 run 筛选时，使用从正式配置派生出的临时配置，只保留一个 `dl_runs` 条目，并把 `experiment_name` 改成带候选名的独立目录，例如 `phase_window_tcn_ablation_g0_screen`。临时配置不得覆盖正式 `phase_window_tcn_ablation` 输出目录。

按时计费时的停止规则：

- 已完成的 Phase 1 run 直接计入 A/B1 基线，不重跑。
- 若 G0/B/D/C 的单 run 筛选已经明显 OOM、NaN、吞吐下降或 N2 指标显著变差，立即停止该候选。
- 若当前 Phase 1 批次还在运行，不要中途为了 G0 或 worker sweep 打断；先拿到正在运行批次的完整基线，再启动候选筛选。
- 任何“完整 4 run 重跑”都必须有明确目的：候选已通过单 run 筛选，且准备作为正式配置或论文结果使用。

### A. 保持当前基线，先建立速度事实

先不要继续改 batch 或模型结构，跑 Phase 1 诊断批，记录真实吞吐：

```bash
PYTHONPATH=src python -m pipeline.run_experiment \
  --config configs/experiment/phase_window_tcn_ablation/phase_window_tcn_ablation.json \
  --dataset-dir data/wv4-formal-hitran-standard-6000 \
  --output-root outputs
```

观察每个 run 的：

- `epoch_seconds`
- `train_seconds`
- `val_seconds`
- `train_samples_per_second`
- `gpu_memory_allocated_mb`
- `gpu_memory_reserved_mb`
- `best_epoch`
- `val_loss`
- `test/extrapolation x_N2 R2`

验收：这是后续所有加速候选的对照组。

省时补充：如果该批次已经启动或部分完成，继续使用已有结果作为 A/B1。不要删除输出或重新启动同一配置；重复运行只会浪费服务器时间，并可能覆盖同名输出目录。

### B. DataLoader worker sweep

当前服务器标称 32 核 vCPU（逻辑核），`num_workers=2` 是保守值。worker 数的有效上限受**物理核数**约束，实测拐点常在 4–8 worker 出现，超过物理核数后基本不再 scale。候选只改 DataLoader，不改模型、loss、batch 和 lr：

前置确认：先用 `nproc`（Linux）/ 任务管理器（Windows）确认**物理核数**，作为 worker 上限的硬参考。

| 候选 | `num_workers` | `persistent_workers` | 目的 |
|---|---:|---|---|
| B0 | 0 | false | 判断是否 worker/进程开销反而拖慢 |
| B1 | 2 | false | 当前基线 |
| B2 | 4 | false | 测试是否能隐藏数据读取/重采样开销 |
| B3 | 8 | false | 物理核数允许时可测试，重点看 CPU/IO 与显存波动 |
| B4 | (B2/B3 选出的拐点) | **true** | worker 拐点确定后，验证 persistent 是否带来额外吞吐 |

关于 B4 的说明：`persistent_workers=true` 让 worker 跨 epoch 常驻，消除每 epoch 的 worker 重启开销。本项目 epochs=80，重启开销被放大，persistent 在 worker 数较大时通常是净正收益。当前正式配置固定 false 的理由是"避免内存压力"，但 B4 用于实测验证这一假设是否成立。

接受条件（改为"找拐点"而非固定阈值）：

- 在 B0→B1→B2→B3 中取 `train_samples_per_second` **不再显著上升**的那个点作为 worker 数；不要求每个候选都比 B1 提升 10%。
- `gpu_memory_reserved_mb` 不接近显存上限
- 没有 DataLoader worker 报错或明显 CPU/IO 拥塞
- B4（persistent=true）相对拐点候选：吞吐不下降且 CPU 内存可接受即采纳

不接受条件：

- worker 增多后 epoch 时间波动变大，或吞吐反而下降（过饱和）
- prefetch 缓冲溢出导致主进程内存异常

二级旋钮 `prefetch_factor`：总缓冲 = `num_workers × prefetch_factor`。默认 2 只在"worker 已到拐点且 GPU 仍饿"时才升到 4；不要在 worker 数未定前调它，否则会混淆瓶颈来源。

省时补充：B0/B2/B3/B4 先只跑代表性单 run，不跑完整 Phase 1。若 B2 或 B3 在前 3-5 个 epoch 的 `train_samples_per_second` 已明显低于 B1，或 CPU/IO 已过饱和，可以提前停止该候选。

### C. torch.compile 小样本试跑

PyTorch 官方建议 `torch.compile(..., mode="reduce-overhead")` 可减少 kernel launch/CPU 调度开销，但其底层走 **CUDA graphs**，**以增加显存换取降低 launch 开销**，且官方文档明确该模式"useful for small batches"。本项目 batch=16 不算小、PhaseWindowTCN 三窗口激活显存是大头，恰好属于 CUDA graphs 收益最差、风险最高的组合，因此必须严控试验条件。

风险依据（联网核实）：

- NVIDIA 官方：`reduce-overhead` 的 trade-off 是 **increased memory usage**，因 CUDA graph capture 使用私有显存池、需要预分配静态 input buffer。
- PyTorch GitHub Issue #128424：reduce-overhead 下出现"GPU memory continuously to grow（每个新 shape 的第二次调用）"。
- CUDA graphs 为**每个见过的 input shape 单独 capture**；本项目最后一个 batch 大概率不是 16 的整数倍，会触发**二次 capture → 显存接近翻倍**。

候选配置：

```json
"performance": {
  "cudnn_benchmark": true,
  "tf32": true,
  "compile": true,
  "compile_mode": "reduce-overhead"
}
```

试验方式：

- 只选一个 PhaseWindowTCN run
- 至少跑 5 个 epoch，忽略第 1 个 epoch 的编译开销
- 对比第 2-5 个 epoch 的平均 `train_samples_per_second`

接受条件（硬门槛）：

1. 编译稳定后 `gpu_memory_reserved_mb` **≤ 38 GiB**（48 GiB 的 80%）。理由：CUDA graphs 锁定私有显存池，超此门槛会挤压后续候选 D 的 batch 上探空间。
2. 第 1 epoch 后显存**不再持续增长**（排除 Issue #128424 的显存泄漏模式）。
3. 吞吐提升至少 15%，显存峰值仍有安全余量。
4. 没有 graph break / compile error / NaN（GradScaler 频繁跳步也视为失败信号）。

代码前置条件（实测前必须处理）：

- **`drop_last` 当前不可配**：`src/dl/cli.py` 的 `_build_loader` 未暴露 `drop_last`，训练 loader 默认最后一个 batch 大小不一致。开 compile 前需先为训练 loader 增加 `drop_last=true` 支持（仅 compile 试验 run 用），否则末 batch 触发二次 capture。这是代码改动，不计入本配置文档，但属于 C 方案落地的前置项。
- `Trainer.save_checkpoint` 已处理 `_orig_mod` 前缀（见 trainer.py），compile 下的 checkpoint 与未 compile 双向兼容，无需额外处理。

铁律（避免叠加风险）：

- **C 与 D 绝不叠加测试**。compile 锁显存池 + batch 放大是双重显存压力，必须各自单独验收。
- 整个 Phase 1 批次不直接开 compile，风险过大。

省时补充：C1 只做单 run，且必须独立于 B/D 候选。若第 1-2 个 epoch 后显存持续增长、reserved 已接近 38 GiB，或出现 graph break/compile error，立即停止，不跑满 5 epoch。

暂不推荐：

- `compile_mode="max-autotune"`：可能更快，但编译时间和显存风险更高，只有 `reduce-overhead` 通过后再试。
- 在整个 Phase 1 批次上直接开启 compile：风险过大。

### D. batch size 小步上探

`batch_size=32` 在旧 24 GiB 环境上 OOM；新 48 GiB 环境显存余量更大，可以重新测试更大 batch，但仍要小步上探并保留收敛验收。

当前实验配置优化器为 **`adamw`，lr=0.00015，cosine scheduler（min_lr=0.000001）**（见 `configs/experiment/phase_window_tcn_ablation/*.json`）。AdamW 属自适应优化器，batch 缩放应走**平方根规则（√k）**而非线性规则——即 batch ×k 时 lr ×√k，保持梯度方差恒定。这是与 SGD 的线性规则（lr ×k）的关键区别。

| 候选 | batch | k=新/旧 | √k 缩放 lr | 说明 |
|---|---:|---:|---:|---|
| D0 | 16 | 1.0 | 0.000150（原值） | 当前基线 |
| D1 | 20 | 1.25 | 0.000168 ≈ **0.00017** | 先不改 lr 跑一轮看 best_epoch 是否后移，再决定是否升 lr |
| D2 | 24 | 1.5 | 0.000184 ≈ **0.00018** | 48 GiB 环境优先测试点 |
| D3 | 32 | 2.0 | 0.000212 ≈ **0.00021** | 48 GiB 环境候选点；通过完整指标后才可转正 |

lr 选择判据（不再用"或"，按规则计算）：

1. D1 先用**原 lr=0.00015** 跑完整 run。
   - 若 best_epoch 明显后移（如从 ~4 涨到 >15）且 val_loss 变差 → 用 √k 缩放后的 lr 重跑。
   - 若 best_epoch 与 N2 指标稳定 → 说明本场景对 lr 不敏感，可不升 lr。
2. D2/D3 用上表 √k 计算的 lr；若 cosine scheduler 启用，**min_lr 也按同比例缩放**（如 D2: min_lr 0.000001 → 0.0000012，避免调度下界偏离）。
3. 注意 NeurIPS 2024 "surge phenomenon"：最优 lr 在 critical batch size 附近不严格遵循缩放规则，因此 D2/D3 的 lr 仍需以完整 run 的 val_loss/N2 为最终判据，缩放规则只作为起点。

接受条件：

- 不 OOM，显存峰值有余量
- `train_samples_per_second` 增益大于 batch 增加带来的收敛风险
- 完整 run 的 `val_loss`、`test x_N2 R2`、`extrapolation x_N2 R2` 不明显变差
- **critical batch size 监测**：若 batch 翻倍但 samples/s 增益 < 30%，说明已过 critical batch size，停止上探（再加 batch 只增显存不增速度，且 generalization gap 风险上升）

注意：batch 变大可能减少 optimizer step 数并改变收敛轨迹。它不是纯性能开关，必须用完整指标验收。

### E. 只减少无效训练，不改单 epoch 速度

早停已经从 25 调到 10。后续只有在曲线证明仍大量浪费时才继续缩小。本项目 MVP best_epoch≈4，patience=10 已足够，**E 的边际收益小，从推荐执行顺序中降级为按需项**，不默认占用机时。

可选候选：

| 候选 | patience | 风险 |
|---|---:|---|
| E0 | 10 | 当前基线 |
| E1 | 8 | 可能过早停在偶然波动前 |
| E2 | 15 | 若发现 best epoch 经常晚于 10-12，可回调 |

接受条件：

- `best_epoch` 稳定早于停止点
- 不牺牲 `val_loss` 和 N2 指标


### G. BF16 替代 FP16（Ada 架构红利）

当前 AMP 用 `dtype=float16 + GradScaler`。RTX 5880 是 Ada，原生支持 BF16，在 Ada 上 BF16 的 Tensor Core throughput 与 FP16 相当。

BF16 与 FP16 的关键差异：BF16 与 FP32 **同为 8 位指数**（动态范围相同），数值上不需要 loss scaling 即可避免梯度下溢。对 PhaseWindowTCN 的 N2 难学组分（小尺度、易被梯度忽略），BF16 的数值稳定性理论上更友好——这不仅是加速候选，也可能间接改善 N2 收敛。

候选配置（零代码改动，只改配置，`AmpConfig.dtype` 已支持）：

```json
"amp": {
  "enabled": true,
  "dtype": "bfloat16"
}
```

试验方式：

- 单 run，与 FP16 基线同 seed 对照
- 重点对比 `test x_N2 R2`、`extrapolation x_N2 R2`、`val_loss` 曲线、`best_epoch`，以及 `train_samples_per_second` 与显存

接受条件：

- 数值稳定（无 NaN/inf；若 val_loss 不劣化即视为成功）
- N2 指标不劣于 FP16 基线
- 吞吐不下降

代码复核项（落地前确认，非阻断）：

- `Trainer.fit()` 在 `amp.enabled=true` 时无条件初始化 `GradScaler(enabled=amp.enabled)`（见 trainer.py:143）。BF16 下 GradScaler 实际无作用（无下溢风险），代码上是 no-op，不阻塞试验；但若 BF16 通过验收并转正，建议把 GradScaler 在 BF16 下显式禁用（`enabled=False`），避免产生无意义的 scale/unscale 调用开销。这是后续代码优化项，不影响 G 方案试验本身。
- 不建议 BF16 与 FP16 混用同一 run；二者选一作为正式配置。

省时补充：G0 不重跑完整 Phase 1。先用代表性单 run 与 A/B1 中同名 run 对照；只有 BF16 在速度、显存和 N2 指标上都不劣于 FP16，才考虑扩展到其它 Phase 1 run。

## 不推荐作为提速方案

### micro-batch / gradient accumulation

它能降低单次 forward/backward 的峰值显存，但会增加每个 effective batch 的 forward/backward 次数。对当前目标“加速训练”不合适。

### activation checkpointing

它通过重算换显存，通常会变慢。当前模型含 BatchNorm/Dropout，checkpoint 还会引入统计和随机性细节；除非显存无法运行，否则不作为默认方向。

### 直接裁剪模型或模态

降低 `acoustic_channels`、`waveform_embedding_dim`、窗口数量或模态会改变实验定义。只有在明确改实验问题时才做，不应混入训练配置优化。

### 继续沿用 batch=32 旧方案

旧方案曾估算 `17GB -> 6-8GB`，但 24 GiB 环境 OOM 已证明该估算不可靠。新 48 GiB 服务器可以重新实测 `batch_size=32`，但必须按候选 D3 验收；在有完整速度、显存、收敛指标前，`batch_size=16` 仍是正式基线。

## 推荐执行顺序

0. **Phase 0 前置确认**：确认物理核数（`nproc`/任务管理器）、确认优化器为 adamw（已确认）、确认 cosine scheduler min_lr（已确认）。
1. 让当前正在运行的 Phase 1 基线（A）继续完成，形成真实速度表；已完成 run 不重跑。
2. 选一个代表性 run 建立候选筛选口径；默认用 `phase_window_tcn_gas_varweight`，若当前已完成另一个 PhaseWindowTCN run，则可直接使用该 run 的 A/B1 结果作对照。
3. **G0（BF16 对照）**：只跑代表性单 run，验证 BF16 是否同时改善 N2 收敛与速度。零代码改动、低风险，优先于 B 试，因为它可能同时解决 N2 与速度两个问题。
4. 做 DataLoader worker sweep（B0→B2→B3，B1 使用已完成基线），先只跑代表性单 run 找拐点，拐点确定后验 B4（persistent_workers）。
5. 在 48 GiB 服务器上按 `batch_size=20 -> 24 -> 32`（D1→D2→D3）逐步上探，先只跑代表性单 run；lr 按 √k 缩放，监测 critical batch size。
6. 对单个 run 试 `torch.compile(mode="reduce-overhead")`（C），严格守 ≤38 GiB 显存门槛，**前置补 drop_last 代码支持**。
7. 只有候选通过单 run 筛选并准备转正时，才扩展到完整 Phase 1 或联合回归。多候选转正时，组合需做一次联合回归 run，不能直接相加收益。

顺序原则：

- 低风险、可能改善 N2 的候选（G0）优先于纯加速候选（B、D）。
- 纯加速候选中，零收敛风险的（B）优先于改变收敛轨迹的（D）。
- 高风险高收益的（C）放最后，且与其他候选互斥不叠加。
