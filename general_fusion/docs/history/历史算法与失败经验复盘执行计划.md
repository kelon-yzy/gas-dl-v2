## 1. 计划结论

历史复盘不应从“把旧模型重新跑一遍”开始，而应先建立可核验的证据链：

1. 先还原每个算法所处的数据、任务、划分、预处理和部署假设。
2. 再区分算法本身失败、信息不可辨识、目标函数失配、实验协议错误和工程假失败。
3. 最后把可继承经验、必须重写的机制、应保留的负对照和暂时关闭的路线映射到 general_fusion 的 A0-A6 阶段。

本计划的最终产物不是所有模型的总排名，而是一套可追溯的历史知识库，能够回答：

- 之前到底尝试过哪些算法和变体；
- 每个结果是在什么数据契约和实验协议下得到的；
- 失败是由信息上限、数据问题、表示问题、目标问题、模型问题、鲁棒性问题还是工程问题导致；
- 哪些经验可以直接继承，哪些只能作为受控对照，哪些路线应永久关闭或等待前置条件；
- 这些结论如何约束 general_fusion 的算法设计、实验顺序、停止条件和论文表述。

## 3. 不变量与禁止事项

以下规则是整个 H0 复盘的硬约束。

1. 历史结论必须绑定来源、版本、数据契约、实验协议和证据等级；没有这些信息只能标记为 unknown，不能补写成确定结论。
2. 不跨项目直接比较绝对误差、R²、MRE 或覆盖率。不同气体体系、浓度范围、采样率、窗口长度、标签定义和传感器物理条件必须分层比较。
3. hydrogen_ng、syngas、tunnel_ventilation、rcdw_mgda 的 ID、split、scaler、输出定义和结论命名空间保持隔离。
4. 新正式主线的 mixture_id 只表达混合物身份，不回退、不重写为 sequence_id。
5. 新正式 benchmark 不依赖 base_condition_id、noise_seed_index、noise_seed；历史项目若使用过这些字段，必须记录为历史协议依赖，不能直接继承。
6. syngas 的 128 步历史结果与当前 512 步结果分离；弃用结果可以作为失败经验，但不能作为当前性能证据。
7. 先区分信息上限与模型上限，再讨论网络结构；任何“大模型没有学好”的表述都必须先排除信息不可辨识、标签噪声和评估协议问题。
8. 机制有效、指标有效、部署有效、论文可宣称是四个独立判断，不能用其中一个替代另外三个。
9. 不复制 V3 历史代码到 general_fusion；复用逻辑时必须重新表达数据契约、主键语义、产物命名和接口。
10. H0 不进行全量长时间训练，不以运行次数替代证据质量，也不因旧路线失败而放宽 current A0-A6 的门槛。
11. 历史负结果和未通过结果必须保留，不得通过更换指标、删除失败 seed、改变 split 或缩小问题定义来制造成功。
12. general_fusion/项目总体规划.md 是当前阶段事实源；本文件是历史复盘执行计划，不建立第二套 A0-A6 状态。

## 4. 证据等级与状态体系

### 4.1 证据等级

| 等级  | 定义                             | 可以支持的结论               |
| --- | ------------------------------ | --------------------- |
| E0  | 只有想法、计划、讨论或文献启发，没有可运行实现        | 只能说明提出过，不能说明有效        |
| E1  | 有代码、配置或模型定义，但没有可信运行结果          | 可以说明实现存在，不能说明性能       |
| E2  | 有 smoke、单批次、单 seed 或局部实验       | 只能支持可运行性或局部现象         |
| E3  | 有正式协议、完整产物、明确 split 和至少必要的重复验证 | 可以支持项目内比较和阶段结论        |
| E4  | 有冻结数据、配置、代码版本、环境、结果和哈希，可独立复核   | 可以支持高强度历史结论、复现实验或正式引用 |

证据等级不等于算法质量。一个 E4 的失败结果可能比一个 E1 的“有效”主张更有研究价值。

### 4.2 结论状态

建议统一使用以下状态，避免 success、failed 等含义过宽：

- planned：仅计划或候选；
- implemented：已有实现，尚未完成正式验证；
- smoke_only：只完成冒烟或局部实验；
- formal_pass：在明确门槛下通过；
- formal_fail：在明确门槛下失败；
- blocked：因外部依赖、数据或工程问题无法判断；
- invalidated：因数据、协议、代码或版本问题失效；
- superseded：被新数据、窗口、接口或协议替代；
- parked：保留观察，但当前不进入主线；
- negative_control：主动保留用于证明某类无效路线；
- unknown：证据不足，禁止强行归因。

每条记录同时保存 evidence_level、conclusion_status、scope 和 confidence。confidence 只表示证据完整程度，不表示性能高低。

## 5. 统一记录结构

复盘先建账，再写叙述。建议在 general_fusion/docs/history/ 下形成结构化登记文件，并由 Markdown 报告引用；Markdown 负责解释，登记文件负责唯一事实。

### 5.1 source_registry

每个来源只登记一次：

| 字段                | 要求                                            |
| ----------------- | --------------------------------------------- |
| source_id         | 稳定、唯一、不可复用                                    |
| project           | 所属历史项目                                        |
| path              | 原始文件或目录的仓库相对路径                                |
| source_type       | 细分来源类型；必须在登记文件顶层 `source_type_groups` 中唯一归入 doc、code、config、test、log、output、freeze 或 commit |
| version_or_commit | 版本、提交、时间点或文件哈希                                |
| date              | 形成或运行日期                                       |
| owner             | 来源责任人或来源角色                                    |
| status            | active、deprecated、missing、conflicted          |
| notes             | 只记录事实，不写推测                                    |

### 5.2 task_contract

每个算法和实验必须挂接一个任务契约：

| 字段                    | 内容                                    |
| --------------------- | ------------------------------------- |
| task_id               | 任务唯一标识                                |
| project               | 历史项目                                  |
| input                 | 原始波形、DSP、统计量、时频特征或组合                  |
| output                | 目标气体、温度、流速或其他量；单位必须明确                 |
| sample_and_window     | 采样率、帧长、窗口长度、步长                        |
| sensor_definition     | 传感器、通道和通道是否异构                         |
| label_definition      | 标签来源、范围、闭合约束和噪声                       |
| group_definition      | mixture_id、序列、工况或其他分组语义               |
| split_protocol        | train、validation、test、OOD、blind 的实际规则 |
| preprocessing         | scaler、归一化、滤波、缺失处理、增强                 |
| deployment_assumption | 推理时可获得的输入与资源                          |
| identifiability_note  | 信息审计、Fisher rank、串扰或其他可辨识性结论          |

### 5.3 algorithm_ledger

算法台账至少包含：

| 字段                   | 内容                                                       |
| -------------------- | -------------------------------------------------------- |
| algorithm_id         | 稳定算法 ID，不以实验次数命名                                         |
| lineage_parent       | 父代算法和改动原因                                                |
| source_refs          | 代码、配置、文档、结果来源                                            |
| input_representation | raw、DSP、phase、statistics、time-frequency 或组合              |
| fusion_form          | early、mid、late、gated、residual、dynamic weighting、solver 等 |
| architecture         | 层级、分支、注意力、时序模块和参数规模                                      |
| output_head          | raw4、softmax、gas_head、ILR/ALR 或其他                        |
| objective            | loss、权重、target scale、约束和正则                               |
| claimed_mechanism    | 该算法试图解决的问题                                               |
| required_observable  | 机制所需的真实可观测信息                                             |
| evidence_level       | E0-E4                                                    |
| conclusion_status    | 统一状态之一                                                   |
| conclusion_detail    | 受控状态下的范围或原因说明；不得把原因拼入 `conclusion_status`                  |
| limitation           | 已知边界、失败条件和不可外推范围                                         |
| disposition          | inherit、rewrite、negative_control、park、close、unknown      |
| disposition_condition | 继续、重写、暂停或重开所需条件；不得把条件拼入 `disposition`                    |

### 5.4 experiment_ledger

每个实验记录：

| 字段                   | 内容                      |
| -------------------- | ----------------------- |
| experiment_id        | 运行唯一标识                  |
| algorithm_id、task_id | 关联算法与任务                 |
| data_version         | 数据包、冻结版本或生成规则           |
| split_and_group      | 实际划分、group key 和 OOD 规则 |
| seed_and_repeat      | seed、重复次数和缺失 seed       |
| config_ref           | 完整配置来源                  |
| metric_definition    | 指标公式、单位、聚合方式和低浓度处理      |
| result_ref           | 结果、日志、图表和 manifest      |
| resource             | GPU、时间、参数量、推理成本         |
| failure_or_exit      | 失败、退出码、NaN、OOM 或空产物     |
| reproducibility      | 是否可重跑、是否已复核             |
| claim_scope          | 允许支持的结论范围               |

### 5.5 failure_ledger

每个失败都按因果链登记：

| 字段                    | 内容                       |
| --------------------- | ------------------------ |
| failure_id            | 失败唯一标识                   |
| algorithm_id          | 直接关联算法；必须与 `experiment_id` 所指实验的算法一致 |
| experiment_id         | 关联实验                     |
| symptom               | 可观察症状                    |
| layer                 | 信息、数据、表示、目标、模型、鲁棒性、工程或表述 |
| hypothesis            | 初始根因假设                   |
| discriminator         | 能区分假设的最小检查               |
| evidence              | 代码、日志、指标、可视化或复现实验        |
| root_cause            | 已证实根因；不能确认时写 unknown     |
| residual_ceiling      | 根因修复后仍然存在的性能上限           |
| scope                 | 只对哪些数据、任务和协议成立           |
| corrective_action     | 修复、重写、隔离或关闭              |
| stop_condition        | 何时停止继续投入                 |
| general_fusion_impact | 对 A0-A6 的具体影响            |

## 6. 分阶段执行计划

### H0-0：冻结复盘规则

预计投入：0.5 个工作日。

执行内容：

- 冻结项目、任务、算法、实验、结果、失败、主张七类对象的定义。
- 建立 source_registry、task_contract、algorithm_ledger、experiment_ledger、failure_ledger 的字段。
- 固定证据等级、结论状态、来源优先级和跨项目比较规则。
- 标记当前事实源：general_fusion/项目总体规划.md 负责当前主线；历史文档只负责证据和经验。
- 为每条高价值结论预留 source_refs、scope、confidence 和 disposition。

交付物：

- 复盘规则与证据分级说明；
- 统一登记模板；
- 历史项目范围清单。

阶段门：

- 任意一条历史结论都能被归入“事实、解释、假设、建议”之一；
- 不存在同一字段由两份文档分别定义的情况；
- 能明确识别弃用结果、未完成结果和正式结果。

### H0-1：历史来源与版本盘点

预计投入：1-2 个工作日。

执行内容：

- 按项目扫描 docs、src、scripts、configs、tests、outputs、logs、freeze、manifest 和 Git 历史。
- 记录每个文件的路径、来源类型、时间、版本或提交、是否仍有效。
- 优先定位实验入口、配置文件、数据生成脚本、评估脚本、结果 manifest 和评审记录。
- 对同名文档、重复结果、移动后的文件、过期配置和缺失产物建立冲突记录。
- 不把全文复制到汇总文档，只保存必要的引用和摘要。

交付物：

- source_registry；
- 项目与版本时间线；
- 过期、缺失、冲突来源清单；
- 每个项目的证据入口页。

阶段门：

- 所有准备进入算法台账的算法都有可定位来源；
- 所有准备进入正式比较的指标都有结果来源和版本来源；
- 未注册来源不得支撑强结论。

### H0-2：任务、数据与物理契约归一化

预计投入：1-2 个工作日。

执行内容：

- 为每个项目建立 task_contract，不改变历史原始定义。
- 对齐输入模态：原始波形、DSP、相位、统计量、时频特征和组合输入。
- 对齐输出：目标变量、单位、浓度范围、闭合约束、低浓度样本和标签来源。
- 对齐采样率、窗口、步长、传感器通道、串扰、噪声、缺失和部署可获得信息。
- 明确 train、validation、test、OOD、blind 的真实 group 规则；保留 mixture_id 语义，禁止用 sequence_id 代替。
- 记录物理可辨识性、Fisher rank、传感器相关性、绝对 TOF 是否存在等信息。
- 对 oracle 特征、后验真值、实验室离线量和推理时不可用输入单独标记。

交付物：

- 项目数据契约地图；
- 输入表示与输出头交叉表；
- split、scaler、增强和部署假设对照表；
- 可辨识性与信息上限清单。

阶段门：

- 每个算法都能绑定到唯一任务契约；
- 每个指标都能追溯到标签、单位、split 和聚合方法；
- 能明确区分“信息不可学”和“模型没有学到”。

### H0-3：算法考古与谱系重建

预计投入：3-5 个工作日，可按项目并行。

执行内容：

- 从代码、配置和结果反向还原算法的真实结构，不以文档中的概念名称代替实现。
- 为每个算法填写 algorithm_ledger，记录输入表示、融合位置、输出头、loss、target scale、参数量和推理成本。
- 按 lineage_parent 连接算法变体，写清楚每次改动试图解决的具体问题。
- 把算法分成基线、表示学习、结构融合、物理机制、动态可靠性、残差修正、求解器/UQ 和纯工程变体。
- 将“有想法但未实现”“实现但无正式结果”“正式失败”“正式通过”分开。
- 记录算法依赖的隐含前提，例如固定通道、固定气体数、随机缺失、真实可用的质量指标或额外测量。

交付物：

- 历史算法谱系图；
- 算法台账；
- 算法卡片集合；
- 每个算法的前置条件、收益假设和失败边界。

阶段门：

- 每个算法都有 source_refs、task_id、evidence_level 和 conclusion_status；
- 同一算法的不同输入、输出头、loss、窗口和数据版本不会被错误合并；
- 提案不能被误标为实验证据。

### H0-4：证据核验与定向复查

预计投入：2-3 个工作日。

执行内容：

- 对照代码、配置、日志、结果、测试、manifest 和文档，检查“写了什么”和“实际跑了什么”是否一致。

## 8. 失败根因分类与判别路径

### 8.1 根因分类

| 层级         | 典型问题                                              | 最小判别                         |
| ---------- | ------------------------------------------------- | ---------------------------- |
| L0 信息与可辨识性 | 观测对目标不充分、Fisher rank 不足、通道高度相关、窗口过窄               | 信息审计、rank、相关性、可观测量对照         |
| L1 数据与标签   | 标签噪声、范围不平衡、split 泄漏、group 语义错误、传感器退化未建模           | 数据契约、分组检查、标签统计、泄漏检查          |
| L2 表示与预处理  | 绝对 TOF 丢失、相位失真、pooling 过度、scaler 覆盖不全、oracle 特征混入 | 输入复原、特征可用性、梯度/消融、部署复核        |
| L3 输出与目标   | 输出参数化不匹配、闭合约束、N2 残差、低浓度 MRE 不稳定、target scale 失衡   | output head、loss、梯度、单位和分目标指标 |
| L4 模型与融合   | 分支交互不足、门控退化、物理分组错误、模型容量与数据规模不匹配                   | 强基线、受控消融、参数量、跨目标误差结构         |
| L5 鲁棒性与外推  | 只测随机缺失、未测真实质量退化、OOD 定义单一、UQ 过宽或未校准                | 缺失/噪声/冲突/OOD/UQ 全矩阵          |
| L6 工程与协议   | AMP NaN、Windows 退出码误判、死配置、空产物、旧数据仍被读取             | 日志、退出码、配置追踪、manifest、重跑      |
| L7 主张与写作   | 把前置条件通过写成目标通过、把架构迁移写成权重迁移、把单一 OOD 数值写成泛化          | 主张-证据矩阵、范围和术语审计              |

### 8.2 统一判别路径

遇到新失败时，按以下顺序检查：

1. 信息是否足够：若不可辨识，停止增加模型复杂度。
2. 数据是否可信：确认标签、split、group、scaler、通道和部署输入。
3. 强基线是否建立：没有 baseline，不能判断复杂模型是否有增益。
4. 输出和目标是否匹配：检查参数化、闭合、尺度和梯度。
5. 表示是否保留关键观测：特别是绝对 TOF、相位和质量信息。
6. 机制是否真正改变了可用信息或误差结构：不能只看结构图和 attention。
7. 鲁棒性是否使用真实退化：不能用随机 dropout 代替所有可靠性问题。
8. 工程和评估是否可信：排除假失败、旧配置和指标计算错误。
9. 最后才判断模型结构本身是否不足。

## 10. 历史方法的处置规则

| 处置               | 进入条件                                 | 允许的下一步                      | 禁止的表述            |
| ---------------- | ------------------------------------ | --------------------------- | ---------------- |
| inherit          | 机制简单、输入真实可得、证据 E3 以上、协议与新主线兼容        | 作为 A1/A2 baseline 或固定组件     | “在所有气体和传感器上都有效”  |
| rewrite          | 研究假设有价值，但旧实现绑定旧 ID、固定通道、旧 split 或旧产物 | 在 general_fusion 接口内重写并重新消融 | 直接复制旧实现并宣称复用     |
| negative_control | 历史上有明确无增益或失败证据，且能代表一种常见误区            | 在 A2/A4 作为对照验证失败是否重现        | 删除负结果或只保留成功 seed |
| park             | 机制未被证伪，但前置观测、数据或校准尚未满足               | 记录 reopen_condition，等待前置条件  | 当前阶段直接进入主模型      |
| close            | 信息上限、部署不可行或关键 gate 已多次失败             | 保留结论和证据，停止投入                | 通过放宽门槛重新包装       |
| unknown          | 来源冲突、结果不完整或根因无法区分                    | 设计最小判别实验，或明确不再追查            | 用经验性猜测代替证据       |

所有 inherit 和 rewrite 项目必须同时记录：

- 前置条件；
- 最小实现；
- 必要消融；
- 失败判据；
- 资源上限；
- 重新开放条件；
- 与历史结果不可直接比较的因素。

## 13. 时间、资源与风险控制

### 13.1 预计工作量

- 总工作量：约 14-18 个工作日。
- 并行日历时间：约 8-12 个工作日。
- GPU 需求：来源盘点、契约整理和大部分根因分析不需要 GPU；只为高价值歧义保留少量定向复查。
- 复盘期间不启动大规模新模型搜索，不以网格搜索代替根因分析。

### 13.2 主要风险

| 风险          | 识别信号                    | 处理方式                                    |
| ----------- | ----------------------- | --------------------------------------- |
| 文档结论与代码不一致  | 文档有指标但找不到入口或产物          | 降级证据，登记冲突，不直接采用                         |
| 旧数据版本混入     | 同名文件、不同窗口或不同采样版本同时出现    | 以 data_version 和 hash 分层，弃用结果隔离         |
| 只整理成功结果     | 台账中没有失败、未晋级和 blocked 条目 | 强制 failure_ledger 与 negative_control 清单 |
| 过早锁定模型      | H0 阶段出现最终模型、超参或长跑结果     | 回退到候选卡，等待 A0/A1 证据                      |
| 把工程假失败归因于模型 | 退出码、AMP、配置和产物不一致        | 先完成 L6 工程核验                             |
| 复盘形成第二套事实源  | 当前计划与历史报告都在定义 A0-A6     | 以 general_fusion/项目总体规划.md 为唯一主线事实源     |
| 历史代码污染新主线   | 旧主键、固定通道和临时命名直接出现       | adapter 隔离，核心接口重新实现并做契约检查               |

## 15. 首轮执行顺序

按以下顺序开始，不提前进入模型搜索：

1. 完成 H0-0，冻结字段、证据等级、状态和比较规则。
2. 并行完成 H0-1 的来源盘点与 H0-2 的任务契约地图。
3. 各项目 lane 完成 H0-3 算法台账，先覆盖强基线、关键机制和关键失败。
4. 对会改变 general_fusion 方向的冲突执行 H0-4 定向复查。
5. 用 H0-5 建立失败根因图谱，再做 H0-6 跨项目合成。
6. 将结果映射到 A0-A6，生成候选研究卡和 kill criterion。
7. 完成反向审稿、冻结复盘包，然后进入 general_fusion A0。

当前阶段的唯一先行任务是建立可复核的历史证据层；在 H0 的阶段门未通过前，不应把任何历史模型直接晋级为 general_fusion 正式主模型。
